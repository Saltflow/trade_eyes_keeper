# 财报数据检查实际效果审计

日期：2026-10-24。全程离线，API请求0；生产Python、配置、prompt、示例及旧结果未修改。

这份审计区分“解析不了”“元数据有意见”“不能自动对齐”“数值抄错”。这些不是一回事。现有业务检查没有与PDF逐项比对数值的功能，不能把检查意见数称为错误财务数据数。

## 样本及直接解析结果

- 230份response.body按SHA256去重为91种。其中41种来自规范样例，排除后真实模型响应50种。
- 标准json.loads与当前parse均45份成功、5份失败。没有一份只因重复JSON键或NaN被当前parse额外拒绝。
- 五份解析失败：旧泸州单块1、旧API元数据1、2023经营附注1、2025截断经营/资产附注2。前3份finish=stop，因此stop不能证明JSON合法。
- 另有3条ConnectionError回执没有response.body，与取得HTTP响应的50份分开统计。
- 45份可解析对象中，28份为当前3.0协议，17份为旧结构；旧结构不是错数据，不自动冒充新协议。
- 当前协议31次原请求有28份可解析，包含256表、2675行、8675个values单元格。
- 直接解析对照没有执行业务validate/table_notes/item_errors/table_errors/period_errors，0业务校验调用、0网络尝试；28个完整模型对象及31份正文逐字段/字符串保持相同。
- 直接展示只有1张kind=attribute的表走已有通用原字段展示，没有修正枚举、补单位、改日期或修改数值。
- index.html为直接解析后的可折叠阅读对照；direct_parser.json保留原文及原始解析对象。没有做新的跨年合并或生产入口切换。

## 实际发送的上下文

31份请求逐项核对：公共prompt、块任务prompt、完整JSONschema、对应规范例均等于当前config/fixtures；没有被传输层裁减。同一块三年的指令相同。128K实验messages与原2023经营块完全相同，仅改max_tokens和thinking。

但以下差别必须说明：

1. 给了各块主题名称，没有把定稿文档每个主题下的账龄、核销、受限等细项全部逐项展开成任务指令。
2. 每块给一个对应规范例，不等于把完整正反例测试集发给模型。经营附注例只有一个“工程承包＋境内”行，没有业务分部×年份宽表反例。
3. 行axis唯一没有明确写进prompt或JSONschema，却在脚本额外检查。
4. numeric列没有分类dimensions，宽表如何转成一行一个确定维度组合没有完整规则。
5. “分行或拆子表”不能保证解决期间问题，因为numeric期间在列，单纯分行仍可能冲突。
6. 原文title/path/basis是自由文本，又被当作精确跨年键；没有独立稳定身份。
7. 同名债券、重复小计、分部合计/抵销的表达缺少完整示例。
8. 允许平均方法、年化未说明，却没有讲清这些行会被第二阶段隔离。

因此，不能说prompt已消歧到位；也不能把后续讨论过、尚未实施的修补方案说成已经发送。

## 结论及尚未执行的变更

- 能证实的解析阻断是5份坏JSON。不能把字段/口径意见当作已拦住财务错数。
- 格式检查能发现部分真实元数据矛盾，但“有诊断价值”不等于“应拦住在线数据”。
- 已验证“模型原文→解析器→保留/展示”可以绕开业务校验，并完整保留当前28份对象。
- 业务schema、期间、维度、缺失原因、任务覆盖及冲突分类，应与解析和展示解耦，作为独立离线审计；不能再借这些意见整表阻断。
- 预算、冻结、防覆盖、原文落盘和解析不丢键等必要保护保留；不能因为没拦到错数而撤掉付费或历史保护。
- 移走业务检查不等于解决跨年身份。不能通过删检查、强行合并未知身份来制造“对齐成功”。
- 本次只新增审计和离线直接解析对照，正式入口尚未切换，prompt尚未修改。新旧历史产物、生产源码和配置均核对未变。
