# 财报与研究请求的缓存审计

核对日期：2026-10-30。范围为四大行FY2019—FY2025的真实请求、回执，以及当前请求构造代码。本次只读审计和本地排列实验，**付费API请求0次**；没有更改冻结prompt、schema、计划、旧输出或生产执行器，没有恢复上传或资料采集。

后续实施状态（2026-10-30）：用户授权后，已在本地提取入口分离完整profile归属合同与本次执行选择；执行块仅位于模型任务尾部和本地调度记录。真实PDF离线验证默认10份全量请求与改前字节一致，单块请求与全量对应请求字节一致。现有审计582份输入哈希未变，未调用模型；其他公共目录、schema、摘要及研究prompt重排仍是建议。下文“当前”布局及指标保留审计时快照。实施证据见[离线验收](../../data/acceptance/fundamental_ownership_fix_20261030/offline_acceptance.json)，使用合同见[财报入口指南](../guide/financial_pipeline.md)。

## 结论与建议顺序

1. 提取阶段输入缓存命中82.25%，最终保留的280个正常任务为81.79%。现有“共同system＋完整财报前缀＋任务尾部”已有效，保留这种方向和20路全局并发。
2. 280个请求各自尾部都有完全相同的12,065本地token的身份／单位／维度目录和歧义示例。这部分应从任务差异之后移到共同前缀。七个附注块还共用5,424token的同一schema，可放在财报之后、具体任务之前。
3. 审计时单独`--block`会收缩财报前的任务归属目录，破坏与全量计划的公共前缀；已按上方实施说明分离“完整归属合同”和“本次执行哪些块”。
4. 摘要的段号、正式研究的阶段prompt都提前造成分叉。摘要只共享少量定义，优化收益有限；正式研究三轮共享大段材料，适合固定职责目录、材料前缀与阶段尾部控制的新版本设计。
5. 缓存只便宜化输入。提取费用78.87%来自输出，不能把命中提升理解成整体费用同幅下降。已有成功结果继续复用，比再发一次“高命中”请求更省。

完整证据位于[审计目录](../../data/acceptance/financial_cache_audit_20261030)：[汇总](../../data/acceptance/financial_cache_audit_20261030/audit.json)、[280块明细](../../data/acceptance/financial_cache_audit_20261030/accepted_blocks.csv)、[排列实验](../../data/acceptance/financial_cache_audit_20261030/layout_candidates.json)、[原输入哈希](../../data/acceptance/financial_cache_audit_20261030/input_hashes.json)、[验收边界](../../data/acceptance/financial_cache_audit_20261030/validation.json)。

## 官方机制及应区分的三层缓存

DeepSeek的KV缓存默认开启，复用的是已持久化的相同输入前缀，不是生成好的答案。当前指南描述三种持久化位置：请求边界、检测到的公共前缀、长输入输出的固定间隔；完整匹配相应单元才可复用。缓存写入需要时间，闲置后通常数小时至数天清理，属于尽力服务。指南的财报例子说明，前两次不同任务可能先促成公共单元，第3次才利用它。[当前缓存指南](https://api-docs.deepseek.com/guides/kv_cache/)

2024新闻提过64token存储单位，当前指南已采用上述前缀单元描述，不能据旧文保证“补齐64token就命中”，也不能承诺固定24小时TTL。[历史公告](https://www.deepseek.com/news/context-caching/)

| 层次 | 复用对象 | 本项目含义 |
|---|---|---|
| 本地资料／解析缓存 | PDF、按来源哈希和解析版本生成的文字及图像 | 减少下载和本地解析；不代表服务商已缓存 |
| 本地成功结果复用 | 已验收的模型输出、对应源文件、请求、schema、模型身份及范围 | 本轮已有57个旧成功块直接复用；同义任务不应为了命中率重跑 |
| 服务商KV缓存 | 消息从开头起的相同token前缀 | 每次仍须传入上下文；输出仍重新推理和计价 |

模型实际看到的内容顺序才重要：外层HTTP JSON换缩进，并不会改变其中的prompt文字；嵌在消息内容里的JSON换键顺序、换行、日期或任务ID则可能改变前缀。角色、内容块和图像也应稳定。本次文本前缀长度使用本地tokenizer，不把base64字符当作文字token；图像另计，只以真实usage判定命中。

Files API可以避免同一图像反复上传，但图像token仍参与计价，不等于KV命中保证；本轮不建议为缓存改动已冻结的图像表示。[图像指南](https://api-docs.deepseek.com/guides/vision/)

当前Chat Completions文档没有给出本项目可依赖的显式TTL或`cache_control`合同；`assistant.prefix=true`是另一项输出前缀补全功能，不能当作缓存开关。[接口参考](https://api-docs.deepseek.com/api/create-chat-completion/)

## 实测：哪个阶段低

使用`sum(cache_hit_tokens) / sum(prompt_tokens)`，只统计有usage的请求，避免平均各调用百分比，也不把输出放进分母。

| 阶段 | 有usage调用 | 输入token | 命中token | 加权命中率 |
|---|---:|---:|---:|---:|
| 四大行提取，含已知重试／未选入最终结果的调用 | 301 | 77,479,035 | 63,728,892 | **82.25%** |
| 仅最终保留的280个提取任务 | 280 | 71,912,802 | 58,815,230 | **81.79%** |
| 最新单公司摘要，含分段和整合 | 12 | 2,959,236 | 28,672 | **0.97%** |
| 同行七问横评 | 1 | 304,086 | 2,048 | **0.67%** |
| 正式研究三轮 | 3 | 1,068,380 | 6,400 | **0.60%** |

提取及新旧摘要合计的输入命中率为78.97%；这个总数会掩盖阶段差异。提取另有140次缺usage，**不按零命中、零费用处理**，不纳入已知token分母。横评、正式研究单独列示，不混入原提取和摘要费用账本。

正常280任务中，statements命中14.32%、capital72.04%、metadata91.13%，大部分附注约87%—94%。冷读在任务间分布不均，不能按最低的一类判断全部缓存失效。先前失败或历史请求也可能影响缓存，缺usage时不能断言是否完成预热。

## 提取：现有布局、漏洞和可直接比较的新布局

当前[请求构造器](../../src/fundamental_data/v2_transport.py)采用：

```text
system：所有块相同的共同要求
user：公司／年度＋完整任务归属目录
      → 全文文字＋已有图像
      → [block:具体任务]＋该块prompt＋schema＋示例＋清单
      → 身份／单位／维度目录＋歧义示例
```

离线核对280份实际请求：仅1种system、28种财报公共前缀；同年报10块的财报及图像前缀一致。各任务`真实prompt_tokens − 本地任务尾部token数`完全一致，28个年度组校准差均为0，支持据此估算公共前缀大小。

### 共享常量被放在任务分叉之后

全部280个请求中的最后两项目录／示例逐字相同：26,760字符、12,065token，但前面已经出现不同block ID和任务文字，后面的相同内容不能单独拿来抵消前缀分叉。七个附注块的schema也逐字相同，为5,424token；它们的具体示例并不全相同，不能一并当作公共示例处理。

建议只重排原有文字，不增加泛化示例，不删除字段：

```text
system：原共同要求
user：共同身份／单位／维度目录＋歧义示例（12,065token）
      → 公司／年度＋完整任务归属目录
      → 全文文字＋原图像
      → 本块schema（七个附注共用同一份）
      → 本块自己的示例
      → [block:具体任务]＋本块prompt＋本块清单
```

280份请求均已在内存中验证重排后的文字片段与图像守恒；没有生成或发送新业务请求。这证明内容没丢，**不证明顺序变化后的模型语义、财务准确性或真实命中率已经通过**。

同一工行2019报告的资本块与附注块：当前相同前缀约226,893本地文字token及4张相同图像；提议布局约239,033文字token及相同图像。两个附注块的共同前缀约从226,895增至244,414文字token。

### 单块CLI另有一个会破坏缓存的前缀变化

[提取入口](../../scripts/build_fundamental_data_v2.py)先按`--block`收缩`names`，再用它生成财报前的`frozen_job_ownership`。因此同一报告单独跑capital时，前面从完整10块目录变成1块目录。

使用真实请求做相同变化后，与全量计划的共享前缀从约226,893文字token＋4图，降到**1,019文字token**。这是离线前缀长度，不是一次新API命中实测。

建议未来的新版本始终使用完整profile归属目录，单独记录本次执行块；block选择留在任务尾部和本地调度记录。现有成功结果不重跑，历史请求不回写。

同样，不应把每块不同的schema或prompt提前塞入system：离线反例使同报告跨块公共前缀只剩约989文字token，原财报长前缀随之失去作用。

## 摘要与三轮研究

### 两个摘要分段

现批次先写“第1/2段”或“第2/2段”，再写两段共有的定义，导致分叉提前。将原段号／本段边界说明完整移到任务尾部、共同定义提前后，文字没有删减：

| 公司 | 现有公共前缀token | 离线重排后 |
|---|---:|---:|
| 工行 | 3,752 | 29,120 |
| 农行 | 3,752 | 24,520 |
| 建行 | 3,752 | 27,415 |
| 中行 | 3,752 | 24,963 |

但两大段正文各只使用一次，最终整合又读取分段输出；这类任务天然有大量新输入，低命中不全是浪费。共同定义只有约2万—2.5万token，不能据此承诺摘要命中80%。不要为了提高比例把两个完整分段都再次塞进每个请求，也不能通过丢材料绕过500k水位。

段范围、年度覆盖、空附件状态必须真实保留；共同前缀可带完整来源覆盖目录，段尾声明本段范围。缓存重排不能冒充此前“农行2024未提供／空附件当失败块”问题已修复。

### 正式研究的三个阶段

[三轮构造器](../../scripts/research_rounds.py)把不同的draft/review/write要求拼到system，然后才放共同材料。实际公共前缀约3,329文字token，在system内分叉；财报与材料虽然在后面重复，仍难复用。

已做一个**未执行的新协议候选**：把三阶段原要求逐字保留成固定职责目录；共同研究材料放在所有请求相同的位置，再放上一轮稿件、图表及本轮阶段控制。离线共同前缀约341,769—341,789文字token，全部原阶段要求及图像保留。

候选需要验证角色选择和独立审稿约束，不能简单删掉阶段要求或降低审稿标准。仅3次请求的冷启动比例也限制命中率，不能照搬10次任务的目标；共同材料的重复输入费有机会减少约US$0.05—0.10，仍属条件估计。

## 能省多少钱

冻结的非峰时费率按每百万token计：缓存输入US$0.003、未缓存输入US$0.15、输出US$0.60；当前网页与本轮冻结值一致。峰时价格是这些数值的两倍，未来费用仍须按执行时段重核，不能改写历史计价。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

已知提取US$10.665927126的组成：

| 部分 | usage计价 |
|---|---:|
| 命中输入63,728,892token | US$0.191187 |
| 未命中输入13,750,143token | US$2.062521 |
| 输出14,020,365token，已包含reasoning | **US$8.412219** |

在保持本轮全部输入／输出量不变、把所有未命中输入都变为命中的不可现实保证情形下，最多也只省US$2.021271。95%等情景只是数学反事实，不是项目的可达承诺。

对正常280任务，按每份报告仅冷读一次、之后全部可复用的**现有布局模型**，输入命中约83.44%；实际最终请求为81.79%。因此不能只通过调整排队顺序期待巨大收益；此前缓存预热及近似模型也限制了这种对比的解释。

新布局的目录前移＋共享schema分组，离线新增可复用量约390万—428万输入token，折合**US$0.57—0.63／同规模28份报告**。其乐观冷读一次模型约89.39%。这包含“开始20个共同目录未命中、每个schema组前2次未命中”的敏感性情形，但没有服务端实测，实际可能更低；局部token边界或新的内容块包装也可能略变。

还有21个有usage的提取回执未进入最终280个结果，已知计价US$0.798581。它们的finish_reason均为stop，不能一概归因输出截断，也不能声称这笔费用全可省；应另查当时的校验和重试必要性。

## 拆分与调度应怎样取舍

- 先保留现有10块、财报完整前缀和20路全局池。高命中的已有成功块保持本地复用；没有成功响应不能因“可能缓存过”就视为已完成。
- 不同任务的问题、清单、段号、执行批号放在各自稳定材料之后；本地路径、运行时间和状态只在确有语义需要时进入消息，否则留在本地回执。
- 若未来新文档冷启动确有大量同时未命中，可试“metadata等必要且短输出的真实任务先发、其他任务后放行”，多文档继续填满全局池。当前metadata平均输出约7,537token，低于多数附注；这只是候选调度依据，不是已经证明的最优排队。不要把整池改回串行，也不要额外发纯预热、保活或重复请求。
- 按章节切财报是减少输入量的另一条路线，不能只看命中率。需要章节／物理页覆盖清单、跨页完整表、比较期、表头、单位、范围与会计政策上下文，不能只抽关键词段落。一次性使用的短输入即使命中低，也可能更省；本轮未验证它相对完整报告的财务覆盖。
- 不把全部335家公司资料塞进一个大前缀，不把每个模块改成携带所有旧模型回答的串行对话，也不为减少调用数而合成一个可能截断的大输出。
- 本地解析／结果缓存键应绑定原件内容哈希、解析／渲染版本、profile、prompt/schema版本、实际模型身份及验收结果。语义所需的年度或来源身份不能为了相同前缀而删掉。
- 同一原件先冻结一次文字和图像，再由这些原字节构造各块请求；避免每次单块执行都重渲染材料、重建不同目录。更改本地解析版本时保留旧版本及页码映射，不为命中擅自清洗金额、负号、单位或比较期。
